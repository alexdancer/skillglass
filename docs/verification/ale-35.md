# ALE-35: browse and explain OpenCode skills

`--agent opencode` adds offline OpenCode discovery and local configured-availability explanations to the accepted shared collection contract. CLI list/read/explain/compare and the browser use the same immutable snapshot. Production commands never launch OpenCode, run plugin hooks, load a skill, evaluate config substitutions or fetch skill indexes. Read-only operations never write sources/settings. See [OpenCode controls](ale-36.md) for the separately validated writer contract.

## Native version and discovery

The recorded rule version is **OpenCode 1.17.15**. It identifies validated rules, not the user's currently installed version or a running session. The installed Homebrew binary reported `1.17.15` in disposable HOME/XDG directories. Verification uses fresh noninteractive `--pure debug skill`, `debug config`, and `debug agent build` processes, with no credentials and an OS sandbox denying network access and reads/writes to the real HOME.

Global compatibility roots are HOME/.claude/skills and HOME/.agents/skills. Their project equivalents are searched from the explicitly selected directory to the nearest genuine Git repository, inclusive. Without Git, only the selected directory participates. No project is selected implicitly from CWD. Global native roots are XDG_CONFIG_HOME/opencode/{skill,skills} (default HOME/.config) and HOME/.opencode/{skill,skills}. Project .opencode/{skill,skills} directories run from nearest to repository root. OPENCODE_CONFIG_DIR adds its singular/plural roots last. Configured `skills.paths` is an array of recursive roots; `~/` expands HOME and relative roots resolve against the explicitly selected project. Relative configured roots without a selected project remain unknown. Optional missing native roots are reported, while missing required configured paths limit coverage.

Native discovery follows directory and manifest aliases and visits nested bundles even below another SKILL.md. External .claude/.agents roots include dot directories; native/configured roots exclude them. The viewer bounds traversal and reports cycles, unreadable entries and exhaustion. Generic explicit roots retain their established direct-child behavior and remain inspection-only unless another native reference reaches the same proven source. Native names come from frontmatter, independently of source identity. Proven directory aliases share one source; same-name independent directories and directories sharing only a manifest remain separate targets. Native route identity includes origin, requested path and context. Identical native descriptors contribute once in first-occurrence order, while global/project routes at the same HOME path retain distinct root/reference IDs on the same physical source, including disabled external routes. Distinct alias spellings remain separate references; generic explicit-root occurrence identities are unchanged.

OPENCODE_DISABLE_EXTERNAL_SKILLS excludes both compatibility families; OPENCODE_DISABLE_CLAUDE_CODE or OPENCODE_DISABLE_CLAUDE_CODE_SKILLS excludes only .claude. Excluded roots remain inspectable with their flag evidence. OPENCODE_DISABLE_PROJECT_CONFIG omits project config and project .opencode roots, while external project scans retain their independent flag semantics. Unsupported or malformed native inputs remain unknown and limit coverage.

## Configuration and permissions

Local configuration follows the order below. Historical runtime observations and later source-inferred corrections are distinguished separately from raw discovery:

1. Global config.json, opencode.json, opencode.jsonc, followed by the recognized extensionless global config input.
2. OPENCODE_CONFIG file.
3. Project opencode.json/jsonc, repository to selected directory.
4. Native directories: global configuration, nearest-to-root project .opencode directories, HOME/.opencode, then OPENCODE_CONFIG_DIR, deduplicated by raw string. Only raw directories ending in .opencode or exactly matching OPENCODE_CONFIG_DIR reload opencode.json then opencode.jsonc, never config.json. An exact configured-global spelling reloads at the existing global entry before project .opencode inputs; a trailing slash or /. is a distinct later entry reloading the same physical pair after those inputs. Repeated load layers retain path provenance without duplicating normalized discovery roots. These alias-order corrections follow pinned source and public adapter regressions, not fresh native execution. Relative, tilde, symlink and other unvalidated configured-directory spellings retain explicit uncertainty.
5. OPENCODE_CONFIG_CONTENT.
6. Managed opencode.json/jsonc in `/Library/Application Support/opencode`, or the supplied native OPENCODE_TEST_MANAGED_CONFIG_DIR fixture override.
7. OPENCODE_PERMISSION, followed by the default agent's permission rules.

The pinned v1.17.15 global loader also recognizes XDG_CONFIG_HOME/opencode/config (default HOME/.config/opencode/config). The viewer observes only metadata at that exact path. Present or uninspectable input produces a global unknown config layer and a native-input problem, unknown eligible permission/availability, incomplete coverage and exit 1. Legacy content is never read, parsed, imported, migrated or written. Presence is observed separately from pinned-source inference about native loading; native TOML validity, migration, enforcement and exact installed-binary/source equivalence remain unverified. Later valid JSON, project-config exclusion and pure mode do not erase this global uncertainty. Extensionless project/custom files are not inferred native inputs.

OpenCode deep-merges objects, replaces arrays, and retains the original insertion position when replacing an existing ordinary key. Native JavaScript property enumeration places canonical unsigned decimal array-index keys from 0 through 4294967294 first, in ascending numerical order; all other keys retain insertion order. The viewer applies that enumeration to object merges, tools, permission tools/patterns and agents, keeping input paths with values. The viewer supports comments and trailing commas, rejects ambiguous duplicate JSON keys and excessive nesting, and reads only bounded regular files. A successfully read exact zero-byte regular JSON/JSONC or required custom config file contributes an empty object and retains a loaded layer with its path/scope. Whitespace-only content and failed reads remain unknown; optional absence remains absent. This is a disk-loading rule inferred from pinned v1.17.15 source, not general parser EOF acceptance or new native runtime evidence. Empty environment inputs remain skipped, whitespace virtual inputs remain invalid, and the extensionless global legacy path remains metadata-only. Empty layers add no keys and never clear earlier uncertainty or permission/tools/default-agent/plugin evidence. Config content and unrelated credentials are never reported. Native `{env:...}` and `{file:...}` substitutions remain unsupported instead of reading secrets or arbitrary files.

Native permission strings normalize to `*` before merging. The complete final context tools boolean map seeds allow/deny permissions after all context layers, including runtime permission; write/edit/patch map to edit and wildcard tool keys are retained. Explicit permissions deep-merge over that seed without moving existing keys before a single enumeration. Consequently seeded skill can precede an explicit wildcard even when the explicit object lists the wildcard first. Legacy per-agent tools and explicit agent permissions normalize within each input before the agent config merge, not at the final context boundary. Explanations preserve the controlling input path and distinguish a synthesized tools rule from an explicit permission rule. The supported default selection is build when default_agent is absent or the empty string, or the exact nonempty locally configured default_agent. Whitespace is not trimmed; implicit build retains configured permissions/tools and hidden/disabled/subagent guards. Skill-relevant built-in profiles are resolved before context permissions and then selected-agent overrides: build/plan are primary with allow; general is subagent with allow; explore is subagent with wildcard deny; compaction/title/summary are primary, hidden and wildcard deny. Explicit mode/hidden/disable fields retain their input paths and override inherited state. Configured custom agents default to mode all, visible, with allow before context/agent overrides. Ineligible default selections stay unknown; implicit fallback when build becomes unavailable is not inferred. These inherited profiles follow pinned Agent.state source, not new native execution or session observation. Wildcards `*` and `?` use native last-matching-rule semantics, slash normalization, optional trailing ` *`, case sensitivity on this Mac and home expansion. Matching follows JavaScript non-Unicode regexp UTF-16 units: `?` consumes one unit, so an astral character matches `??`, not `?`. The viewer maps every unit, including BMP units and both surrogate halves, injectively to a distinct non-metacharacter rune before its linear-time regexp evaluation; astral literals remain two matched units without BMP collisions. Paired JSON escapes and literal replacement characters remain supported. A raw JSON string containing an unpaired surrogate escape is explicitly unsupported before Go decoding can replace it: its input layer and effective permission/availability remain unknown with real input provenance, incomplete coverage and exit 1. This is not a claim that native JSON rejects the string; later valid layers cannot erase this interpretation gap. Source explanations identify the selected action, rule, input path and configuration layers. Allow maps to available, ask remains ask, and deny maps to disabled with permission denied. Display filters never recompute permissions or precedence.

Hidden, disabled and subagent-only configured default agents cannot establish native availability. Recognized agent/agents markdown is inspected recursively, including dot directories and directory/file aliases; mode/modes markdown is recognized only at the direct level. Metadata-only presence, inspection failures, broken links, cycles, unsupported entries and traversal limits conservatively make effective targeting or native acceptance unknown before source explanations are built. A different filename can target the selected agent through frontmatter; presence does not prove that it actually does. No markdown content is read or executed. Legacy mode overrides remain unknown. Runtime CLI --agent selection, saved/session approvals, account/organization remote policy and managed preference effective values are unverified. Presence or inaccessible metadata of relevant managed preferences limits coverage. A valid local config inference does not claim actual session tool enforcement. Invalid permission shapes/actions, config substitutions, FIFOs, oversized inputs and broken config links do not silently fall back to allow. Each loaded layer is validated before normalization and deep merge. Present permission must be a supported action or ordered rule object. Exactly todowrite, question, webfetch, websearch and doom_loop require scalar allow/ask/deny when present; other known Rule fields and arbitrary tool keys accept a scalar action or flat pattern-to-action object, including wildcard tool keys. The same raw-layer validation applies to every agent before merge, including unselected agents. Top-level and agent tools must be boolean-valued objects; agent containers and entries must be objects; default_agent must be a string; hidden/disable must be booleans; and agent mode must be subagent, primary or all. Present null is invalid at these seams. Plugin retains only the evidenced outer array check, and skills/paths/urls retain their object and string-array checks with presence-aware null rejection. Absent fields, empty objects/arrays and false flags retain their valid meanings. Every loaded agent entry is checked, including unselected entries. A present top-level legacy mode, including null, remains unsupported uncertainty with its real input path. This is bounded schema inference for interpreted availability fields, not universal native config validation. Later valid settings cannot erase an earlier rejection. Known definitions remain inspectable with unknown availability/permission, incomplete coverage, exit 1 and the rejecting input path.

A definition without description is listed by the installed debug command and remains loadable by exact name, but v1 1.17.15 guidance excludes it. It therefore reports explicit-only. Later documentation describes `metadata["opencode/autoinvoke"]`; the pinned v1 source does not implement that field, so the viewer does not infer a 1.17.15 state from newer documentation. Generic-parser differences remain unknown rather than claiming native acceptance of malformed manifests.

## Precedence and managed sources

The installed v1 discovery path stores one definition per name, but loads discovered manifests using unbounded concurrent Effect.forEach. Pinned source and repeated native observations therefore do not establish deterministic project/global precedence. Equal-name eligible independent sources remain separate, with related-source IDs, unknown precedence and an explicit concurrent-overwrite reason. The viewer does not invent a winning source or label another source shadowed. This follows the parent contract's winning/shadowed explanation requirement where known, with remaining uncertainty explicit; it is not an acceptance waiver or an observed winner. All five retained historical collision samples selected the project path, not mixed winners. The unbounded concurrent source loader, rather than observed variation, prevents a guaranteed future winner. Running-session outcomes remain unobserved; known unique local names retain their configured permissions.

The native debug skill command returns raw definitions before agent permission filtering. Its presence alone cannot prove allow, ask or deny. The native agent's resolved ordered rules were validated separately. No inference session or tool call was started.

XDG_CACHE_HOME/opencode/skills is inventoried as managed cache content with an excluded cache-only route. Neither cached bytes, .opencode-version nor a plugin folder proves current index activation. The viewer never fetches `skills.urls`; configured remote indexes make effective discovery/precedence unknown. Cache-only sources also remain unknown when native configuration or remote/plugin activation is unverified; unavailable is used only when the known native routes establish exclusion. An independently discovered native alias into cache content participates through that alias, while ownership stays managed. Cache ownership uses canonical scope and does not merge independent copies.

Configured/local plugin hooks can change config and native capabilities dynamically. The viewer records nonempty plugin input presence and its declaring config path separately from pinned-source inference that registered origins may retain hooks after later empty lists. Registration starts from the completed global config aggregate, so a list replaced by an empty global list before that boundary does not create plugin uncertainty. Later custom/project/native-directory/inline/managed registrations persist independently of the final plugin array; local hook uncertainty likewise persists. OPENCODE_PURE excludes these external plugin registrations/hooks without waiving other unknown inputs. The viewer limits coverage and marks native effective state unknown, including cache-only activation, while preserving ordinary discovery references. This does not establish that a particular plugin loaded or a particular hook ran. It does not execute hooks, guess a plugin identity from folder names, or scan every package cache. Explicitly inspected canonical cache bundles expose managed provenance and unsupported controls. Remote accounts, plugin-generated skills, v2 runtime behavior and embedded customize-opencode content remain unverified; the embedded skill has no local bundle and is reported as an inventory gap.
