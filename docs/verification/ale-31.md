# ALE-31 Hermes read validation

The viewer supports `--agent hermes` for list, read, explain, compare, problems and the terminal browser. This is read-only. Availability uses the ALE-26 explanation contract and the same filters and terminal renderers. The [Hermes collection modules](../../internal/collection/) implement the version-specific rules below; the [README](../../README.md#build-and-use) owns common commands, filters and browser keys.

## Recorded native version and provenance

Reference version: Hermes 0.20.0 on macOS, source commit `5a16635f409e0f5e3d754bb6256bd27707bcec4c`. Relevant installed source files were clean at that commit, with SHA-256 hashes recorded in the receipts. This pins inferred rules, not an observation of the current installed application or running session.

The initial metadata/index evidence remains preserved in the coordinator's original ALE-31 native receipts. Its legacy runner, `tools/verify_hermes.py`, is retired: it now refuses before resolving arguments, creating fixtures/output, or importing native startup code. The legacy runner imported native startup before establishing adequate containment; its receipts remain historical, with unknown containment effects, not fresh or fully contained startup/catalog validation. The bounded helper below covers environment/configuration only through `tools/verify_hermes_policy.py`. Every helper invocation has a disposable HOME/profile/project/config environment and an OS sandbox denying network, child processes, reads outside fixture/code/runtime, and writes outside that fixture. Owned canaries must verify that boundary before native imports. Machine defaults `/etc/hermes` and `/etc/codex` are modeled absent. Installed-source `.env`, `.op.env` and config contents are excluded.

No plugin initialization, native catalog refresh, full CLI startup or inference session is run by repair validation.

## Behavior and containment evidence

Native full-content metadata uses the same opening/closing-fence interpretation as the index, without the 4,000-character window. An EOF closing fence without its final newline, or a YAML `...` terminator, does not establish native metadata even when generic parsing succeeds. Prompt conditions and explicit names use that full-content interpretation; portable validation requires native framing. Generic metadata and complete read content remain intact.

Hermes-specific YAML checks separate bounded whole-document constructor validation, native mapping-root requirements, and confidence in consumed fields and effective mapping keys/values, following aliases and merge precedence. Consumed sets, omap/pairs and tagged ancestors cannot establish ordinary Go mapping/list facts. Valid unused special containers do not taint selected fields, and a set-tagged merge operand does not change a normal effective map into a set. Overridden merge entries do not taint a supported replacement; effective implicit boolean keys remain distinct from quoted string keys. Plain implicit `yes/no/on/off` spellings supported by pinned PyYAML as booleans, implicit sexagesimal numbers, and consumed `!!binary` bytes are not accepted as Go-decoded native string evidence. Quoted, block and explicit `!!str` scalars remain supported. Index-window and full-content fields are checked separately; JSON plugin roots are not interpreted as YAML. Profile/managed plugin policy confidence follows effective per-leaf replacement. Generic manifests, metadata and full read content are preserved. Unsupported native construction or collection types leave frontmatter interpretation unknown because ordinary native frontmatter has separate non-mapping and line-parsing fallback behavior; they are not treated as definite skill rejection. Profile and managed configuration with unsupported tags also retain unknown policy rather than asserting native empty/default, fail-open, or last-known-good fallback behavior for an unobserved process. These bounded checks do not claim general Go/PyYAML equivalence.

## Explicit evidence gaps

- No native writer is advertised. Enable, disable, removal of project overrides and deletion remain unverified capabilities.
- No running session, model invocation, session-local home/platform override, secret capture, or reload was observed.
- General dotenv interpolation, multiline or unclosed bindings, quoted policy keys, non-UTF-8 normalization and secret providers are not evaluated. Plugin config expansion is bounded to behavioral Hermes environment keys; unsupported/unresolved references are unknown.
- Machine managed policy is excluded from fixture evidence. Its real installed values and enterprise behavior were not observed. Explicit fixture managed roots exercise the supported policy semantics.
- Native Python plugins are not executed; their registration names, load errors and effective skills are unknown.
- Bundled installation plugins and pip entry points are outside this bounded home/project survey, and are called out in scope gaps. Their absence is not presented as complete machine-wide discovery.
- Legacy flat `.md` explicit loads and malformed frontmatter fallback are outside the strict SKILL.md bundle contract; unsupported native parse cases remain unknown.
- OS portability beyond the inspected macOS environment is unverified. Platform-specific disabled settings refer to messaging surfaces, not an invented universal OS configuration.
- Full native CLI skill listing was not run because startup can migrate configuration or seed bundled skills. The original metadata/read probe is preserved as historical evidence from the retired runner; only the bounded environment/configuration helper remains runnable.
- Independent Standards/Spec reviews and no-mistakes execution are coordinator-owned stages; their status is recorded in the run receipts, not inferred from this verification guide.
