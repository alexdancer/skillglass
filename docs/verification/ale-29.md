## Evidence and capability limits

Filesystem roots, parsed settings layers, original/resolved references and plugin manifests are **observed** facts. Availability, invocation policy and precedence are **inferred** from those inputs and version-bound rules. Running-session participation and reload are **unknown**. Every writer remains unsupported. Native visibility settings target names, which can affect independent copies; plugin settings target whole plugins. Neither is exposed as an isolated source writer.

Malformed relevant native inputs produce `native-input`, incomplete coverage and unknown permission. Permission arrays require non-null string elements; consumed boolean settings require non-null booleans. Unsupported invocation frontmatter retains unknown invocation confidence through model-only restrictions; an explicit override excluding both invokers can still establish disable. Unknown installation-registry schemas do not establish inactive sources. Installation scope must be user/project/local, installPath must be absolute, project/local records require an absolute projectPath, and present projectPath/version fields must have supported non-null string shapes. Version strings have no semver restriction. Registry uncertainty cannot establish either activation or inactivity. Local marketplace source activity is independent of installed-cache identity, including when its manifest remains unverified. Remote-marketplace activation, missing registrations and cache-only content remain unknown; explicit plugin disable and a proven nonapplicable/stale registered path are separately excluded. An ordinary alias into managed plugin content does not prove activation. When no native reference is eligible, an unresolved native route preserves overall unknown availability even if another route is excluded; an inspection-only viewer alias does not defeat proven native exclusion. Name-based visibility, Skill permission and precedence use an eligible reference's native name, not an excluded alias's name. Equal-priority independent definitions and shared eligible references with different command names have unknown native winners. Every eligible name remains a possible competitor at its matching reference's rank; an unresolved same-name contender can withhold another source's winner confidence without affecting unrelated names or known higher winners. A definite higher-rank definition establishes lower-source shadowing even when the identity of the top winner remains unknown; availability evidence is inferred while precedence identity remains unknown. These aggregation and naming boundaries are covered by `tests/acceptance/ale29_shared_reference_test.go`. Noncanonical names and hidden ordinary bundle loading are not advertised as validated.

Homepage confidence uses the no-base default WHATWG parser from [National Library of Norway whatwg-url v0.7.0](https://github.com/nationallibraryofnorway/whatwg-url/tree/v0.7.0), pinned at `0c3b19565226a26c151d721319130f402d48cb7f` through Go module tooling. It retains recoverable validation errors, including missing/extra slashes and backslashes. Supported parse failure (such as missing special-scheme host or port overflow) prevents positive activation with a specific parsing explanation. Supported success can establish the homepage portion of activation confidence; it is not full native schema validation. File, opaque and non-HTTP schemes do not receive a blanket host restriction. No Node or Claude process is invoked by browsing.

The parser's domain-to-ASCII implementation has documented skipped IDNA conformance failures, including false accepts for malformed ASCII A-labels. A per-call `WithPreParseHostFunc` observes the domain before normalization and returns the host unchanged. This experimental hook is pinned and covered through public regressions. For special schemes, percent-decoded non-ASCII domains and case-insensitive `xn--` labels remain **unmodeled**, with native acceptance explicitly unknown; malformed percent decoding is also conservative unknown. Bracketed IP literals, opaque hosts and Unicode paths do not enter that IDNA rule. Checking only the normalized hostname would lose malformed A-labels such as `xn--ASCII-`. Parser capture state is local to each assessment, never shared across requests.

Independent private-module vetting records agreement with all 25 native census cases, 871 passing bundled WPT parser leaves and 543 passing no-base corpus cases. The proposed coverage rule supports 514 and marks 29 unmodeled, with no supported mismatch in that corpus. Default upstream IDNA tests skip 98 leaves; explicitly enabling them exposes 87 failures (79 false rejects, four mappings, four false accepts). These are known unsupported upstream coverage, not waived project checks or proof of universal conformance. The four false accepts are excluded before normalization. Native-valid Unicode/IDNA domains can therefore remain unknown. Final vet receipt and all limits are indexed in the repair handoff.

The census supports the relevant parsing semantics without proving Claude's implementation or full URL equivalence. Other URL forms remain bounded by parser coverage and native observation limits. The adapter retains explicit activation uncertainty for manifest fields outside name/version/skills/homepage/repository.

Recognized field names establish confidence only after their raw presence and JSON shapes agree with the bounded contract. Omitted optional version/repository/homepage/skills retain their existing behavior. Explicit null is distinct from omission: present name/version/repository/homepage must be non-null strings, and present skills must be a non-null string or array of non-null strings. Homepage additionally passes the supported URL assessment. Repository strings have no URL restriction, version strings have no semver restriction, and each raw skills path must be exactly `.` or start with `./` before topology/containment checks. Unsupported spelling retains managed inventory with a specific unknown activation and reference-eligibility reason. Empty arrays remain valid. Missing `./missing`, arrays containing supported missing paths, and `./extra/../extra` retain positive path-form confidence: recorded 2.1.282 catalogs load valid commands even when native validation reports missing paths or internal dotdot. The sealed six-case catalogs independently establish that `"extra"` and `""` reject and omit commands. Unsupported array-element uncertainty follows the documented per-path contract, with no native array-rejection observation claimed. Dot root has historical native proof; `./` root follows public/documented proof. The bounded spelling check adds no directory-existence requirement or blanket dotdot rejection. Invalid supported shapes retain inspectable inventory, managed provenance, namespaces and field-specific unknown reasons where a source is discovered. Numeric version remains nonpositive without requiring a fallback source. Explicit skills "."/["."] expose the root bundle, while [] is a valid explicit empty declaration that suppresses root fallback. These 15 native shape controls are bounded evidence, not exhaustive manifest schema validation.

These documented assumptions remain unverified: enterprise filesystem precedence and local/remote/MDM managed enforcement; main-checkout fallback for linked worktrees; non-Git ancestor behavior; runtime loading of newly visited directories; launch flags such as `--add-dir`, bare/restricted/safe modes and `--setting-sources`; existing workspace trust; plugin aliases in permission enforcement; account sync, bundled skills and legacy command files. The product does not inventory legacy command files as skill bundles or infer account activation from downloaded folders. Session and scope explanations disclose these limits.

Official references for assumptions and rule interpretation are [skills](https://code.claude.com/docs/en/skills), [settings precedence](https://code.claude.com/docs/en/settings), and [plugin manifests](https://code.claude.com/docs/en/plugins-reference). Native observations above take priority over newer documentation where they differ.
